Ploof performance report / 30 July 2026

JSON gains 74.6%; plaintext gains 103.7%. The clear lead remains open.

Remaining hot-path issues were profiled, fixed, and measured without relaxing Ploof's bounded-memory or HTTP rules. Final ReleaseFast medians are 1.987M JSON and 2.107M pipelined plaintext requests per second: ninth of nine runnable JSON entries and eleventh of eleven plaintext entries.

base revision dfe29652eeff + optimized working tree FrameworkBenchmarks 523534bb6145 Zig 0.16.0 · ReleaseFast server median of 3 × 15 s confirmations

Verdict

No performance lead can be claimed. Ploof trails the recorded same-host JSON leader by 17.6% and the plaintext leader by 90.6%. Exact benchmark capacities and used-range decoder reset removed the dominant per-request clearing cost. A true copied wire-batch prototype regressed plaintext by 3.1% and was reverted; the retained direct-send burst still performs one syscall per response.

These are engineering comparisons, not official TechEmpower ranks. Client and server share one desktop, multiple unrelated background processes consumed CPU, and Round 23's official run used three dedicated 56-core machines. Same-host execution is useful for finding large gaps; official placement still requires TechEmpower infrastructure.

Implemented contract

GET /json

Instantiates { message = "Hello, World!" } and invokes Ploof's JSON serializer on every request. The body is not a cached JSON string.

application/json; charset=utf-8 · 27-byte body · dynamic serialization

GET /plaintext

Uses a static 13-byte body and Ploof's normal HTTP response path. HTTP/1.1 keep-alive and pipeline depth 16 are exercised.

text/plain; charset=utf-8 · 13-byte body · no disk logging

Both responses include accurate Date, Server: Ploof, and Content-Length. The build is libc-free. Correctness is covered by a runnable response-contract test.

Final fixed capacities per worker are 128 connections, 128 request slots, 32 body workspaces, 128 × 2 KiB receive buffers, 2 KiB pipeline storage per connection, 28 response-body bytes, a 256-byte response-head workspace with 8 fields, 2 response chunks, 256 SQ entries, and 512 CQ entries. Bounds match this application's contract; framework defaults remain unchanged.

After splitting request-body and response workspace capabilities, this response-only app starts 32 worker threads plus the main thread: 33 threads total, with no gzip decoder pool. All storage remains startup-allocated and bounded.

Remaining work to take a clear lead

A “clear lead” means at least 5% above the best competitor median with five or more confirmations and non-overlapping 95% confidence intervals on isolated infrastructure. On these measurements that means at least 2.532M JSON req/s and 23.469M plaintext req/s. The latter exceeds this co-located wrk ceiling, so final proof needs a separate load-generator machine.

1. Coalesce without copied wire staging — blocking priority

The copied wire-batch prototype regressed and was removed. Next experiment should reuse existing response storage with a bounded gather send across complete ordered responses, retaining an iovec cursor for partial sends. Stop on request-slot, iovec, or SQ pressure; preserve observation, close semantics, backpressure, and startup memory budgeting.

Why first: Ploof still needs 9.7× current plaintext throughput to lead. One send call per response remains the largest structural difference, but another copied staging buffer is not the answer.

2. Profile the new JSON ceiling

Capacity and reset fixes moved JSON within 17.6% of the leader, invalidating the old profile. Re-profile on isolated hardware and change only the new top site among serialization, secure clearing, parsing, direct send, and timeout handling. Require a randomized five-run gain.

3. Prove gains on isolated client/server hardware

This desktop was heavily contended during final retest, including unrelated Godot and desktop workloads using many cores. Do not tune around that noise. Run client and server on separate pinned hosts, performance governor, fixed clocks where available, and at least five randomized A/B confirmations.

4. Keep static planning generic

Static plaintext heads are now compiled and Date-patched. Extend eligibility only when normal applications expose another measured static shape. Do not special-case TechEmpower or cache the dynamic JSON body.

5. Preserve capability separation

Request gzip and response workspace planning are now separate. Add compile-time capability combinations only when a route needs them; keep exact slab bounds and the response-only no-gzip regression test.

6. Retune only after gather-send topology changes

Measure cycles/request, CQEs/request, SQEs/request, sends/request, timeout operations/request, cache misses, and wire-batch fill. Then repeat request-slot, connection-slot, receive-buffer, SQ/CQ, and batch-byte sweeps. Current values stay fixed until the topology changes.

Do not add framework-specific shortcuts until generic hot paths have been measured. Any capacity change stays fixed, bounded, startup-allocated, and covered by compile-time memory budgeting.

Standards and regression gates

  • JSON object remains instantiated and serialized for every request. Never replace it with a static {"message":"Hello, World!"} wire response.
  • Plaintext may use a static body, as TechEmpower permits. Date and Server headers remain present and correct.
  • Direct-send burst is bounded at 16 responses per reactor event and adds no heap allocation. Future gather sending must be fixed, startup-budgeted, and covered by partial-send tests.
  • No removal of parser validation, response ordering, slow-client handling, timeouts, backpressure, or cleanup invariants. Hoist validation only when its inputs are compile-time constants.
  • Final gate: 936/936 build steps and 8,672/8,672 tests passed across Debug, ReleaseSafe, ReleaseFast, TSan, integration, package, and compile-failure checks. Benchmark numbers use ReleaseFast only.
  • All 16 public fuzz families passed in Debug, ReleaseSafe, and ReleaseFast: 48 campaigns, four shards and 100 scheduled runs per campaign. Campaigns were run serially because top-level parallel execution intentionally locks the shared fuzz cache.
  • TigerStyle structure check passes. Every Zig file is at or below 750 lines; the changed request-head decoder is exactly 750.
  • Performance gate: five isolated runs, zero socket/non-2xx errors, correct response identity/body/headers before and after, median gain ≥5%, and no p99 regression over an agreed bound.
  • Use a separate load generator before declaring plaintext leadership; this host's top-ten cluster is client/kernel limited near 22.35M req/s.

Reproduction

Build and run Ploof:

zig build techempower
./zig-out/bin/ploof-techempower

Verify identity and contract before timing:

curl -i http://127.0.0.1:8080/json
curl -i http://127.0.0.1:8080/plaintext

Final measured commands:

/tmp/ploof-wrk/wrk -t8 -c512 -d15s --latency \
  http://127.0.0.1:8080/json

/tmp/ploof-wrk/wrk -t8 -c4096 -d15s --latency \
  -s /tmp/pipeline.lua http://127.0.0.1:8080/plaintext -- 16

Contract test:

zig test -OReleaseSafe techempower.zig

Limitations

  • Shared desktop, loopback topology, powersave governor, and unrelated background CPU activity prevent publication-grade statistics. Unrelated Godot and desktop work consumed many cores during the final retest and was left untouched.
  • Competitors were measured sequentially. Background load changed over the long build/run window, so close competitor ordering is not meaningful. Ploof's gaps are large enough that this does not change the conclusion.
  • Container overhead differs from Ploof's native process. Containers used host networking; Ploof's disadvantage is much larger than plausible container variance.
  • Round 23 repository was archived on 24 March 2026. Exact historical dependency reconstruction is no longer possible for EDAP; may-minihttp required a newer builder only.
  • No official composite score exists for Ploof because five database/cache categories are absent.
